## 1. 总体结论与产品目标

保留**共享基表 + 持久增量表**的核心模型，围绕统一读写、可靠冲突检测和审阅合并重建实现。原评审已发现错误结果、写穿 MAIN、并发丢失修改、快照失效及越权读等问题，当前代码尚不能作为产品发布。

建议首版定位为：**PostgreSQL 受管普通表上的 live 数据草稿，支持审阅后原子合并。** 首批场景可选择配置、价格、规则、标注和审核数据等能接受明确 SQL 支持范围的业务。

完整用户流程：

```text
登记业务表
    → 创建分支
    → 在分支事务中编辑、查询
    → 查看 diff 和约束/冲突检查结果
    → 固定待审阅的变更版本
    → 授权人 apply
    → 查询可重试的合并结果、审计记录
    → 清理过期数据
```

首版以一个经过认证的 PostgreSQL 17 构建为目标。发行方式在 S04 完成最小原型后、S05 开始前冻结：优先验证 typed delta + OverlayRelation + 明确的 BranchModify 接口；在当前 PostgreSQL 源码仓库中允许评估小范围内核适配。若无内核补丁安装是硬性要求，必须由纯扩展原型证明同一支持矩阵成立，或者明确缩小矩阵。不能把依赖内核补丁的实现标成通用 PGXS 扩展。

这里的隔离承诺针对受管表的行数据。序列、通知和外部函数副作用有各自的契约，不承诺任意 SQL 或函数副作用都能随分支回滚。

S04 的发行、权限与支持范围决策是后续实施的前置条件；未满足真实工作流要求时按 §2 的评审缺口回到设计，不以竞品存在为放弃本路线的理由。

## 2. Review 意见、候选方案与待处理缺口

### 2.1 应坚持的技术方向

- 先证明统一的单会话读写语义，再认证并发协议；M2 的必要能力通过后才退出到 M3。
- SELECT 与 DML 输入共用 OverlayRelation；typed delta 保存原类型键、不可变首次基线和当前行。
- 同分支写事务串行；apply 对 MAIN 锁后校验，并将数据、终态和请求结果放在同一事务提交。
- seal/revision 绑定被审阅的变更；幂等请求处理客户端未知提交结果。
- 所有入口采用同一能力表；未认证功能明确拒绝。独立真实副本与状态模型验证结果，不能让共享同一错误实现的两个入口互相充当证明。
- 原型的生命周期概念和 D/U/I 操作分类可复用；旧 CAS、advisory、NOTIFY 组合及固定 D→U→I 顺序不自动构成正确性证明，仍按新协议验收。

### 2.2 产品价值与比较口径

产品目标是让变更集可以被查看、编辑、审阅、授权、原子合并和追踪。live 草稿、同库多分支、按增量保存数据，以及 editor/applier 分工，是本路线需要验证的价值。pgrun、Neon、DBLab、Dolt 等可作为调研对照；竞品的具体功能、限制和价格不作为本计划的既定前提。

| 维度 | overlay 的目标与成本 | 评审要求 |
| --- | --- | --- |
| 数据新鲜度 | 未覆盖行随 MAIN 的语句快照变化，覆盖行保留草稿 post-image | 明确 live 与固定时点副本的差异；长寿命草稿的冲突按真实工作负载测量 |
| 分支资源 | 共享 MAIN 和执行实例，持久状态以增量为主 | 测量 delta、目录、查询与 GC 成本，不承诺分支数量没有上限 |
| SQL 兼容 | 需要逐项认证关系、类型、约束、语句和客户端 | 用目标 schema/SQL 样本决定范围；覆盖不足触发重新设计 |
| 审阅与合并 | 行级 diff、revision、授权 apply、原子结果记录 | 这是待实现能力；从其他副本提取的变更集也可以设计类似流程 |
| 权限分离 | editor 可编辑草稿，直接写 MAIN 的权限单独控制 | 必须解决 G02；不能只在选中分支时验证没有写穿 |
| 发行 | SQL、C 扩展或内核适配具有不同安装前提 | 逐环境实装；不能把“使用 PostgreSQL”视为任意托管服务均可安装 |

### 2.3 发行方式与执行候选

S04 对下列候选形成采用或拒绝的记录，选定一条主实现，再进入 S05。初期优先验证 typed delta + OverlayRelation + BranchModify；不长期维护多套完整执行器。

| 候选 | 可行性原型必须证明 | 代价与边界 |
| --- | --- | --- |
| SQL / PL/pgSQL：视图 + INSTEAD OF 触发器 + search_path | overlay 读写、原生类型/约束、缓存计划及所有入口；editor 无直接 MAIN 写权仍能编辑 | schema 限定名称会改变路由；批量写成本、ON CONFLICT、权限和安装权限需实测 |
| C 扩展 | planner/executor/utility 统一接入、逻辑行身份、原生执行职责与纯 PGXS 安装 | 预加载、自定义扩展与目标 PG ABI 是否可用，按目标部署实际核对 |
| 小范围内核适配 | 明确的 BranchModify 接口、完整支持矩阵及对应 PG 构建 | 记录内核补丁、发行包与长期维护成本，不能描述成无补丁通用扩展 |
| 副本 / CoW 沙箱 + 逻辑解码提取变更集 | 在独立副本执行 SQL，提取键、旧值、新值及事务边界，验证审阅与 MAIN 冲突处理 | 副本 SQL 可用不等于变更提取、DDL、序列、副作用与合并均受支持；它改变 live 契约，选用前必须重写相关步骤 |

视图候选示意：

```text
branch schema ob_b42：
    VIEW ob_b42.orders = OverlayRelation 查询
    INSTEAD OF INSERT/UPDATE/DELETE 触发器 → 分支写入 typed delta
use_branch → 受控选择 search_path / 分支上下文
```

本仓库 PG17 文档说明了[视图上的 COPY FROM](../../../doc/src/sgml/ref/copy.sgml#L512)和[视图上的 MERGE 动作要求](../../../doc/src/sgml/ref/merge.sgml#L178)；[计划缓存代码](../../../src/backend/utils/cache/plancache.c#L616)会检查 search_path。这些只证明接入点存在，R05/R06/R07 仍须通过完整分支语义和权限测试才能关闭。schema 限定名称、准备好的计划、函数内 SQL 和分支外写入不能遗漏。

视图实现可作为独立参照，但其结果仍须先用原生表副本校验，且不得复用被测合并函数作为 oracle。副本提取方案可评估 `REPLICA IDENTITY FULL` 等前镜像来源；seal/revision/apply 的职责可复用，具体数据与版本契约需要独立验证。

### 2.4 从实际需求确定支持范围

S04 使用至少一个内部真实库或获授权合作方的 schema、代表性 SQL 及调用频率评估覆盖；优先了解 FK、ON CONFLICT、触发器对目标链路是否必需，不能仅凭场景名称判断。默认边界见 §3，量化标准统一见 §12.5。

S09 先在隔离副本中让真实 Agent 使用单表窄流程；S11 按当前已交付范围重放 SQL 并报告覆盖，S15 在 M2 所有必需能力就绪后完成最终兼容门禁；S21 验证完整用户流程与有效 apply。需求反馈决定后续范围，尚未达到验收的能力持续标为未认证。

## 3. 支持矩阵与范围取舍

下表是 S04 冻结前的 GA 候选边界。G01 若启用条件任务，必须同步更新本表与对应验收。M1 只实现其最小子集；任何一项未达到验收要求，就必须从实际发布的能力表中移除并在执行前拒绝。

| 能力 | 首版目标 | 边界 |
| --- | --- | --- |
| 关系类型 | 显式登记的普通、持久化 heap 表，具有稳定 PRIMARY KEY | 初期不支持分区、继承、FDW、临时表和物化视图写入；无 PK 表不能加入 |
| 表范围 | 一个分支可修改多张受管表 | 非受管表的业务写入在分支上下文中报错，不落回 MAIN |
| 分支模式 | live | MAIN 未修改行随后续语句快照变化；不提供跨事务冻结快照 |
| 事务隔离 | 先认证 Read Committed | RR、Serializable、两阶段提交在单独验证前明确拒绝相关组合 |
| 查询 | 普通 SELECT、过滤、投影、JOIN、聚合和子查询 | 对受管表采用同一 overlay 语义；系统列、行锁子句等逐项列入能力表 |
| 写入 | 单目标 INSERT/UPDATE/DELETE、多行操作、INSERT SELECT、RETURNING | 输入读取 overlay；复杂写入组合在通过测试前拒绝 |
| 主键 | 写入后保持不变 | 首版修改主键明确报错 |
| 约束 | NOT NULL、CHECK、PRIMARY KEY；受支持定义的普通 UNIQUE | 写入时检查当前可见 overlay，apply 时由 MAIN 最终检查；跨行活性问题见下文 |
| 默认值、生成值 | 普通 DEFAULT；序列/identity 有明确的共享分配契约 | M1 先要求显式 PK；M2 验证共享序列分配和 apply 保留已分配值，禁止 apply 再执行 nextval；含未认证生成列定义的表拒绝登记 |
| 复杂写语句 | 首版可明确拒绝 ON CONFLICT、MERGE、COPY FROM、修改 CTE | 先完整拒绝所有入口，后续按语义逐项开放 |
| FK、触发器、规则、RLS | 首版先拒绝受影响的受管表/操作 | 包括被外键引用的表；登记和执行时都检查，防止 MAIN 后续 DDL 改变能力 |
| 并发 | 多读者，同一分支的写事务串行 | 不同分支可以并行；apply 与 MAIN 写入有真实版本冲突检测 |
| 客户端 | 参数化 SQL、prepared statement、事务连接池使用方式 | 以事务范围分支上下文作为推荐接入方式；会话模式需要专用连接和重置契约 |
| 类型、排序规则 | 先认证常用内置类型以及明确的 PK 比较定义 | 自定义类型、扩展 opclass、非确定性 collation 等在未认证前拒绝登记；测试 typmod、NULL、TOAST、编码和类型 round trip |

live 模式下，MAIN 的后续修改可能使现有草稿与 MAIN 合成后的视图不再满足某些跨行唯一约束。首版应保证“分支写入时按当前可见视图检查、apply 时做最终检查”，不能声称长期存活的 live 草稿始终满足全部跨行约束。需要持续满足约束的业务须采用更强的隔离或不同的分支模式。

### 3.1 暂缓的扩展方向

长期持久 snapshot、分支嵌套、自动列级 merge/rebase、同分支高并发写、任意 DDL 分支化、广泛 FK/触发器/RLS 兼容和多 PG 大版本支持，都在首个可用产品闭环之后推进。每项引入独立的语义契约和测试证据，避免功能扩张重新破坏已经确认的隔离与合并能力。

G01 可以根据已冻结工作流启用有限的 FK/ON CONFLICT/触发器组合；这不代表广泛兼容已经纳入首版。未启用的组合保持拒绝，覆盖率按真实样本计算。

## 4. 目标架构与核心不变量

模块名用于划分职责，是否新增同名文件取决于实际共享的数据结构和实现边界。

| 模块 | 职责 | 必须保持的不变量 |
| --- | --- | --- |
| Branch Catalog / Registry | 分支、受管表、ACL、schema 版本、revision、合并记录 | branch_id 来自真实目录；普通角色不能直接读写内部 delta |
| BranchExecContext | 每语句绑定 branch、调用者、权限身份、模式、快照策略、元数据版本 | 一条语句的目标分支不随嵌套调用漂移；错误/回滚后上下文一致 |
| OverlayRelation | MAIN 与 delta 的统一读视图 | 所有读取和 DML 输入使用同一关系语义；谓词不能使被覆盖行重新出现或使 delta UPDATE 消失 |
| DeltaStore | 类型化键、首次修改基线、当前行、墓碑、revision | PK 使用原类型比较；base version 不因后续普通 DML 改变；I/U/D 转换有明确模型 |
| BranchModify | 分支约束、写入、RETURNING、分支内版本处理 | 成功写入只改变 delta；不支持的语句在执行前报错 |
| BranchApply | 写集冻结、MAIN 版本验证、原子合并、结果记录 | 校验和修改不能被 MAIN 并发写入穿插；成功提交后每项增量去向明确 |
| Lifecycle / GC | seal、discard、过期与增量清理 | 终态不可写；清理可以重试；终态回收不影响正在读取的快照 |

读语义固定为：

```text
Overlay = (Main ANTI JOIN 全部 DeltaKeys) UNION ALL 未删除的 DeltaAfterImages
```

每张受管源表使用一张供分支共享的 typed delta 表，并以 `(branch_id, 原类型主键)` 定位增量。按需增加查询索引，避免每建一个分支就增加一组物理表。分支首次触碰表时绑定 schema 版本；表登记、delta 创建和依赖管理需要事务性完成。

首版以完整 post-image 简化读取，并保留首次修改的 base version。审阅与冲突展示需要的 base image 可在首次触碰时一并保存，是否采用列掩码压缩由后续测量决定。ctid+xmin 可以作为保守的实现候选，但其有效范围必须明确：表重写、逻辑恢复、长寿命分支跨越事务 ID 回卷等情况不能无条件沿用旧 token；VACUUM、冻结和 tuple slot 重用也需纳入验证。稳定版本机制若依赖追踪 MAIN 的所有更新，需要另行设计和验证该覆盖范围。

完整 post-image 意味着覆盖整行，包括分支没有修改的列；首版不承诺列级自动跟随 MAIN。live 下每行的首次修改基线也不等于全库创建分支时的共同快照。INSERT 后 DELETE 取消覆盖时重新显露当前 MAIN 的规则，以及逻辑键、冲突 token、审阅 revision 的区分，采用[原始架构诊断](review_2026-09-25.md#architecture-diagnosis)中的明确契约，并在 S04/S06 固定到测试。

### SQL 执行接入

先用关系表达式和真实副本建立正确性参照，再优化执行。M1 必须验证下列接入点：

- UPDATE/DELETE 的读取能够使用 OverlayRelation，包含只有 delta 的行；行身份不再被限定为 MAIN ctid。
- 可复用的原生表达式、投影、RETURNING、约束和权限逻辑继续使用；明确列出分支路径承担或拒绝的 ModifyTable 职责。
- planner、executor、utility 三类入口采用同一份能力判定，覆盖 nested SPI、函数内 DML、EXPLAIN ANALYZE、prepared statement 和客户端批量执行。
- 内部元数据操作按具体对象和受控执行用途识别，不因整个 schema 被列为保护区就允许任意用户对象绕过。
- 不在 ExecutorRun 内继续靠顶层 CmdType 和少数计划形状决定是否写入 MAIN。

纯扩展路线和内核接口路线在 M1 只进行有针对性的可行性验证，不长期维护两套完整执行器。S04 结束、S05 开始前必须选定一个主实现，并记录安装方式、SQL 能力和维护成本。

## 5. 生命周期、审阅与原子合并

建议用户可见的状态为：

```text
ACTIVE --seal--> SEALED --apply--> APPLIED
   |                |
   +----discard-----+-----------> DISCARDED
```

ACTIVE 接受编辑，SEALED 固定待审阅的增量。sealed 固定的是变更集，MAIN 未修改行仍遵循 live 语义，因此审阅界面必须展示基线与草稿的 diff。需要重新编辑时，显式 reopen，递增 revision 并作废旧审阅依据。

`applying` 如保留，应是实际同步协议中的内部状态，不能依赖另一个事务看见未提交状态来冻结写入。同步靠事务锁，最终状态和 MAIN 修改在同一事务提交。

### 分支写锁与快照

所有分支写事务、seal/reopen、apply、discard 通过同一分支事务锁串行化。读取依靠 MVCC，在原快照上已经开始的读取可完成；后续语句发现分支终态时按明确契约报错，不能自动切到 MAIN。

取得写锁之后重新验证 branch 状态、schema 与权限。锁的取得位置需要与有效执行快照一起设计：尽可能在读取输入前建立保护；如果锁等待期间的变化无法在既定快照下安全处理，返回可识别的重试错误，要求整事务重试，不在半条语句执行后偷偷刷新快照。

首版不宣称无死锁。对多关系操作规定一致的访问次序，并用 PostgreSQL 的死锁检测及回滚处理仍可能出现的竞争。

### apply 协议

1. 获取分支写锁，校验调用者、SEALED 状态、expected revision、schema 版本和请求标识。
2. 确定稳定写集，检查变更行数/字节数是否在原子 apply 限额内。
3. 对 MAIN 中存在的目标行取实际写锁，在锁后比较基线版本；对不存在的键通过实际 INSERT 的唯一性机制处理竞争。
4. 按明确顺序执行 MAIN DML，保留标准约束语义，检查每条操作的实际影响行数。D→U→I 顺序不构成任意唯一约束/FK 组合都可合并的证明，未支持的组合明确拒绝或作为冲突返回。
5. 写入合并结果记录，将分支置为 APPLIED，并使本次写集在逻辑上不再可写；与 MAIN 修改一起提交。

任意错误使全部 MAIN 修改回滚，SEALED 分支继续可检查。大规模合并若需分批提交，应定义新的发布语义；首版采用大小上限保证一次 apply 的原子性，不能把批次提交包装成全分支原子合并。

### 审阅与结果重试

以下为建议接口职责，具体 SQL 签名在实现前单独确定：

| 接口 | 作用 |
| --- | --- |
| `diff_branch` | 分页展示 base/current image、操作类型、涉及表、revision |
| `validate_branch` | 返回结构化约束错误、schema 变化和当下可见冲突；结果是预检，apply 必须重新验证 |
| `seal_branch` / `reopen_branch` | 固定待审阅 revision；重新编辑使旧审阅失效 |
| `apply_branch` | 接收 expected revision 与请求标识，只合并被审阅的版本 |
| `branch_status` / `apply_result` | 客户端断线后判断请求是否已提交，获得稳定结果 |
| `discard_branch` | 幂等结束分支，说明是否已有 apply 结果 |

合并记录至少包含 branch、revision、请求标识、执行者、执行时间、影响行数和变更摘要，并与 MAIN DML 同事务写入。事务内记录的执行时间不能冒充精确提交时间；外部会话能读取已提交的结果记录，才构成提交成功的证据。客户端提交后失联，用相同请求标识重试时返回原结果；同一请求标识对应不同 revision/内容时拒绝。权限检查也适用于结果查询。

审阅授权必须绑定 revision；任何修改都使旧授权失效。首版采用行级冲突，报告表、键、冲突原因和允许展示的 base/MAIN/draft 值。需要修改基线时，通过显式、可审计的冲突处理生成新 revision，禁止普通 UPDATE 悄悄改写 base version。自动列级 merge、自动 rebase 后续独立实现。

行级版本检查只覆盖写集。依赖其他行或谓词的业务条件，应显式声明并在 apply 内用足以保护该条件的锁/隔离协议验证；一次普通 SELECT 预检不提供提交时保证。

## 6. 权限、schema 与运行维护

### 权限

分支 reader、editor、applier 分离。目标 editor 由表所有者/管理员授权分支编辑，结合源表 SELECT 与分支 ACL 检查，不要求持有源表 INSERT/UPDATE/DELETE 权限；受控内部身份只写 delta。applier 需要对应的合并授权及 MAIN 写入权限。退出分支、另开连接或使用 schema 限定名时，editor 直接写 MAIN 仍应返回 42501。S04/S13 必须证明这种授权路径，不能通过给 editor 源表写权让原型通过。

内部 delta/元数据不授予 PUBLIC 原始访问；内部权限提升按操作和对象限制。源表读取撤权、分支编辑撤权、applier 写权限撤销分别检查，diff、冲突明细、审计和结果也使用同一授权边界。可选分支绑定角色不替代上述默认权限分离，未实现前不宣称支持。

首版拒绝未实现的 RLS/触发器/FK 组合。表登记时检查一次不够，执行及 apply 时还要验证当前能力和 schema 版本。普通角色测试、权限撤销后重试和跨分支访问都属于发布门禁。

### schema 与计划缓存

维护受管表依赖和 schema 版本。活动分支存在时，破坏列布局、主键定义或语义的 DDL 拒绝执行，或显式将绑定标成失效并禁止继续写入/合并。不能让 rename/drop/rewrite 后的旧 delta 被按新布局解释。

MAIN/branch 切换、权限和 schema 变化必须影响计划有效性；进行中的语句使用不可变上下文。为 prepared statement、generic/custom plan、PL/pgSQL 缓存和游标规定可测试的行为。连接池推荐在显式事务中设置分支，事务结束正确恢复上下文；分支失效不自动退回 MAIN。

### 运维能力

- 限制活动分支数、存活时间、delta 行数/字节数、单次 apply 大小、事务等待时间；超限有明确错误和可观测状态。
- 提供每分支大小、变更数、最近活动、写锁等待、apply 耗时、冲突分类、清理积压等统计。配额和可用性判断不依赖不可靠的缓存计数。
- GC 只清理满足状态与保留策略的记录，任务可重试；终态元数据、审计保留和大 delta 的物理回收分开管理。若物理清理异步，应明确区分“终态不可写的数据”与错误遗留的可写 delta。
- ERROR、取消、SAVEPOINT 回滚、连接退出后，锁、上下文和临时内存均有可验证的回收路径。普通操作数据使用 query/rescan context，不依赖 TopMemoryContext 手工管理整批结果。

### 持久化和恢复

Delta、元数据、MAIN 修改和 apply 结果使用 PostgreSQL 的事务/WAL，但仍需验证 extension 对象和数据的完整备份覆盖。

物理恢复要测试 MAIN 与 delta 的一致状态、未提交 apply 的回滚以及已提交结果的可查询性。逻辑备份尤其需要处理源表 OID 重绑定和 ctid/xmin 变化：不能直接把备份里的 OID、物理版本 token 当作恢复后仍有效。保留稳定的表标识、schema 信息和必要基线；恢复后执行受控重绑定/重新验证，在完成前禁止 apply。若首个发行版只认证物理恢复，应明确这一限制，并提供有证据支持的分支导出/恢复流程；静默遗漏草稿数据不构成可接受的备份支持。

发布前必须选定并验证至少一条完整恢复流程。复制、逻辑解码、standby 分支查询和大版本升级逐项列能力表，不凭“普通表有 WAL”推定全部兼容。

G05 的前台影响预算与 G06 的传播策略属于本节待补充的实施契约，按 §2.5 指定步骤关闭；§12 的单查询内存和 delta 配额不能替代它们。

## 7. 实施阶段与完成定义

不依据历史 V3 的“9/9 完成”估算剩余工作。M0 先固化复现并封堵危险入口；S04 在原型证据上冻结发行与范围，M1 结束更新后续工期。每阶段退出时执行下表所有必需步骤，M2 还包括 S04 启用的条件任务。

| 阶段 | 必须通过的步骤 | 退出结论的范围 |
| --- | --- | --- |
| M0 | S00–S03 | 环境可信、问题可追踪、指定危险入口封堵、基础 API 正确；其余 OPEN 仍阻止发布 |
| M1 | S04–S09 | 最小统一读写与上下文成立；只认证已验证子集 |
| M2 | S10–S15 | 冻结支持矩阵内单会话语义、权限和 schema 边界成立 |
| M3 | S16–S18 | 写集互斥、MAIN 冲突与原子 apply 成立 |
| M4 | S19–S21 | 审阅版本、可重试结果和公开用户流程成立 |
| M5 | S22–S26 | 声明的恢复/部署、资源限制和生命周期成立 |
| M6 | S27–S30 | 性能、长跑和同一候选版本的全部发布门禁成立 |

M2 与 M3 可以交替开展实现工作；M3 的阶段验收以 M2 必需单会话能力通过为前提。已知错误输出不能复制进 expected 充当正确性证明；当前未发布扩展继续采用平铺 1.0 约定。

### 7.1 单步必须具备的内容

每个 S 步骤均遵循下面六项；后文步骤卡给出对应具体内容：

1. **输入**：依赖步骤已通过；记录待改源码 SHA、工作区差异、构建及支持矩阵版本。开始时填写执行者和复核记录负责人，不能只写“开发中”。
2. **执行**：按步骤限定的模块和设计进行可评审修改；新增设计先落文档。若核心契约改变，先更新相关步骤和用例，再实现。
3. **产物**：源码差异、测试用例、规范/错误码更新及明确的数据布局变化。临时 SQL 和 `/tmp` 中的复现必须进入版本管理，不能成为唯一证据。
4. **验收**：运行本步所有必测 case、所有已关闭评审问题的回归 case，以及依赖关系涉及的基础 regress/isolation。环境出错、超时、SKIP、缺用例均不算通过。
5. **通过**：满足本步数值/状态断言和共用门禁；同一源码版本在两个重新初始化的测试集群各通过一次。S00/S01 的基础设施检查不代表产品行为已经通过。
6. **证据**：每步保存环境 manifest、精确命令、退出码、原始日志、断言结果、清理结果及复核结论。代码、SQL 定义、构建参数或相关依赖改变后重新验证，不能沿用旧 SHA 的 PASS。

步骤状态为 `NOT_STARTED / IN_PROGRESS / BLOCKED / FAIL / PASS`。失败后记录失败 case 和最小复现；修复后重跑受影响的门禁。文档更新、编译成功、返回行数正常、预期输出零差异，均不能单独把步骤改成 PASS。

### 7.2 问题处置与阶段状态

- `OPEN`：未解决。`CONTAINED`：已临时封堵，例如禁用危险入口；仍需指定正式处理步骤。
- `FIXED`：目标语义实现，映射用例与回归通过。
- `RESTRICTED`：首版明确不支持，所有相关入口拒绝且没有副作用，文档/能力表一致；不能写成“该功能已实现”。例如主键更新、长期 snapshot、COPY FROM 可采用这一处置。
- R14 是存储设计改进，R15 包含行级冲突的能力边界；不能伪造二者都是原先失败的功能测试。
- 早期阶段可以通过本阶段范围，其他问题继续 OPEN。验收报告必须同时列出 PASS 范围和 OPEN 问题；发布时所有必需项都要 FIXED 或符合已冻结范围的 RESTRICTED，不能留有 CONTAINED 项。
- 未修复问题的诊断可以预期发现缺陷，但必须输出产品断言 FAIL，并与通过的产品门禁分开。禁止把错误结果录入产品 expected，或把 known failure 计入 PASS 数。

### 7.3 共用强制断言

受管业务表的非 apply 写入不得改变 MAIN；每个用例从独立 MAIN 会话验证。验证数据内容、NULL、重复行、受影响行数和 RETURNING，不能只验 count。没有 ORDER BY 的结果按多重集比较；有 ORDER BY 时比较规定的顺序。

每个错误用例同时断言 SQLSTATE、错误类别、MAIN/分支 delta/状态是否按契约回滚。禁止无条件捕获并忽略异常。测试自己的失败使用独立标记（例如 `OB_ASSERT_FAIL`），驱动必须据此非零退出；SQL 中故意返回 `false` 也必须导致非零退出。

所有非故障注入用例中，非预期 ERROR/FATAL/PANIC、崩溃、连接丢失、死锁、超时均为 FAIL。并发或故障用例允许的错误必须逐 case 声明 SQLSTATE、发生阶段和后置状态；不能允许“任意错误都算冲突”。

### 7.4 补充意见的关闭规则

G01–G06 进入与 R/A/P 相同的追踪和复核流程。设计取舍要有理由、已启用能力要有 case 和实际结果；尚缺时间盒、资源预算或复制策略时，对应步骤不能 PASS。S04 的分支选择若新增步骤，必须同步依赖图、能力矩阵、驱动清单与最终发布门禁。

## 8. 环境、执行入口与证据

### 8.1 隔离环境

S00 要生成 `test/acceptance/run.py` 和 JSON manifest；下列路径是计划交付物，不是当前已可运行的工具。驱动必须满足：

- 使用与候选源码匹配的 PG17 独立安装、扩展副本、独立 PGDATA、Unix socket 和端口；拒绝缺少测试标记的既有 PGDATA，停止/清理前核对 data_directory 与 PID。
- 记录 PostgreSQL/扩展源码版本、dirty diff、编译器、编译选项、OS/CPU/RAM、locale/encoding、GUC、客户端与扩展安装路径，以及已安装 `.so`/SQL 的 SHA256。禁止覆盖共享安装或依赖 PATH 中未知的 pg_config。
- debug 配置启用 assertions 和调试符号；性能使用独立 release 构建。两者必须来自同一候选源码。首次运行默认 UTF-8、UTC、`fsync=on`、`full_page_writes=on`、`synchronous_commit=on`。
- 常规/恢复测试保留 autovacuum；需要确定性 VACUUM 调度的单个用例可暂时关闭并显式 VACUUM，单独记录，不能外推为常规运行验证。
- fixture 默认 fresh database；需要测试重启/持久化的 case 明确跨重启保留。普通行为测试设置每语句 30 秒、每 case 120 秒上限；显式等待点有独立期限，超过期限失败并输出等待关系。性能/长跑使用自身固定时限。

现有 Makefile 的 PGXS 路线已经能在独立安装上运行 4 个 regress 与 5 个 isolation。S00 将以下真实入口封装，并在证据中展开实际绝对路径；若 S04 选定内核适配，改用匹配源码构建，不能继续指向旧 PG：

## 11. 验收用例的最低内容

### 11.1 fixture、oracle 与错误码

基础 fixture 至少包含 `t(id integer PRIMARY KEY, color text, v integer NOT NULL CHECK(v > 0), note text)`，初始三行分别为 `(1,'red',10,'base')`、`(2,'green',20,'other')`、`(3,'blue',30,NULL)`。独立表增加普通 UNIQUE；另建不同布局的第二张表、类型表、大 TOAST 表、无权限私有表。每个 case 从声明的初始状态开始，不能依赖前一 case 留下的数据。

静止 MAIN 下，参考连接在独立的原生表副本上执行相同受支持 SQL，比较结果、RETURNING、影响行数及错误。live MAIN 改动时使用独立实现的状态模型，显式输入 MAIN 变更和分支 I/U/D；不得调用被测 overlay 合并函数产生参考结果。对顺序不确定的结果使用类型正确的多重集比较，不能用拼接字符串或仅行数比较。

测试使用的逻辑 API 由 S04 映射为确定的 SQL 签名。早期步骤可以用受限测试入口构造尚未公开的状态，但必须记录该事实，不能借此认证公共 API；S19/S21 必须从公开入口复验。测试入口不得绕过正在验证的锁、版本或权限逻辑。

初始错误契约如下，S04 冻结细节。任何修改必须连同 case 和用户文档一起变更：

| 条件 | SQLSTATE / 类别 | 后置要求 |
| --- | --- | --- |
| 未支持的语句、模式、主键修改 | `0A000` | 业务执行前拒绝，MAIN/delta 不变 |
| 权限不足 | `42501` | 无越权读写，错误不包含私有行值 |
| 分支不存在 | `42704` | 选择和数据不被隐式替换 |
| 分支终态、schema/token 失效、审阅 revision 不符 | `55000`，细分类别明确 | 禁止隐式回到 MAIN；旧授权不能 apply |
| MAIN 首次基线冲突 | `40001 / base_changed` | 整个 apply 回滚；不能自动更新基线后重试 |
| 锁等待后输入快照无法安全承接 | `40001 / snapshot_stale` | 整事务重试，不在半条语句刷新快照 |
| PK/UNIQUE、NOT NULL、CHECK 违反 | `23505 / 23502 / 23514` | 失败语句/事务无部分提交；apply 同键 INSERT 竞争按唯一性冲突报告 |
| 同请求标识对应不同内容 | `22023 / request_mismatch` | 不执行第二次 apply |
| 超过确定的资源/配额限制 | `54000`，注明限额种类 | 不留下部分业务修改 |
| 受控取消、锁超时、死锁测试 | `57014 / 55P03 / 40P01` | 按用例检查事务及资源恢复 |

只有明确标成可重试的 `snapshot_stale` 或 `40P01` 才由驱动重试整个事务，最多 3 次并记录每次结果。`base_changed` 需要冲突处理，不能通过无穷重试掩盖。SQL 中的序列共享分配按单独契约验证，不能把允许的序列空洞错误归为 MAIN 业务表写穿。

### 11.3 确定性并发与原子性 case

调度使用 isolationtester 的显式步骤、数据库锁等待或测试同步点。sleep 只能作为超时保护，不能作为“另一会话一定已走到某行”的证据。每个 case 必须保存实际等待点和最终行值。

| case | 规定时序 | 必须观察到的结果 |
| --- | --- | --- |
| SERIAL-1 | W1 修改后保持事务；W2 同键修改；W1 commit/abort 两种分支 | W2 等待或按契约事务重试；双提交自增为 12，W1 abort 则仅 W2 的修改生效 |
| SERIAL-2 | writer 与 freeze/seal，各自先取锁 | writer 先成功的增量包含在固定写集中；freeze 先完成则 writer 拒绝 |
| SERIAL-3 | A 同事务写入并 freeze/apply，返回后暂不 commit；B 从旧可见 active 状态尝试写入 | A commit 后 B 拒绝，不能形成终态可写 delta；A abort 后 B 可按契约重试成功 |
| SERIAL-4 | discard 与 writer，两种先后顺序；discard commit/abort | 成功写入有活动/显式丢弃记录；终态不可新增 delta；abort 不丢已有数据 |
| SERIAL-5 | 两个 apply，同请求及不同请求 | MAIN 至多一次发布；同请求最终同一回执，不同请求按已结束状态处理 |
| SERIAL-6 | apply 与 discard，同时竞争同分支 | 一条合法终态路径；discard 不能撤销已提交 apply，MAIN/结果与状态一致 |
| CONFLICT-1 | MAIN 把 v=10 改为 99 未提交；分支要发布 11；apply 等待后 MAIN commit | apply 报基线冲突，MAIN=99；禁止静默变成 11 |
| CONFLICT-2 | MAIN 并发 DELETE；apply UPDATE/DELETE，各自先获得行锁 | 每条结果可由锁顺序解释；未覆盖其他提交，影响行数正确 |
| CONFLICT-3 | MAIN 和分支 apply INSERT 同一个原来不存在的键，两种胜者 | 唯一约束决定一个成功，失败方整个事务回滚；无重复键或覆盖 |
| CONFLICT-4 | 两个分支同一基线修改同键后先后 apply | 第一个成功，第二个冲突；修改不同键的对照可分别成功 |
| CONFLICT-5 | 首次修改后 MAIN A→B→A，或 MAIN 只修改另一未触碰行 | 同键按版本契约冲突；另一行修改不被 apply 覆盖 |
| SNAP-LOCK | writer/生命周期锁等待期间有人提交 delta；随后 DML 消费输入 | 不使用过期输入静默写入；需要重试则精确返回 snapshot_stale，重试后结果正确 |
| SNAP-RESCAN | 一条查询暂停在首次扫描后；另一会话提交；原查询 rescan；再开始新查询 | 原查询保持自身快照，新查询按 RC 看新数据 |
| ATOMIC-1 | 两表各三种 delta，在 S18 各暂停点 ERROR/cancel/终止连接 | 失败无部分 MAIN 发布，基线和 delta 可恢复；成功则整体提交 |
| ATOMIC-2 | reader 已开始，另一事务 apply 并随后 GC | 原 reader 按原快照完成；新业务语句按终态契约处理；无半个新旧视图 |

S16/S17 的每个规定时序至少重复 20 次。死锁专用用例可以预期 `40P01` 并检查回滚；正常协议用例出现未声明死锁则失败。不能用“没有 shared→exclusive 升级”代替完整锁图和调度证据。

G01 若启用 S12a/S12b/S12c，必须在运行前增加独立 case 组、初始状态、精确结果、权限/并发/回滚子项及最终负责步骤；缺失任何一项不能让对应条件任务或 M2/S30 通过。

## 12. 资源、性能、活性与业务预算

这些数值是**待实施版本的首轮验收预算，当前未测，也不是已有性能承诺**。S04 在指定硬件与场景上冻结预算版本；如业务需求要求调整，先形成带理由的设计变更，保留旧结果，重新运行受影响验收。不得把预算留空或事后无记录改大。

### 12.1 参考配置与限额

- release 参考主机至少 8 个可用 CPU、16 GiB RAM、50 GiB 可用 SSD 空间；记录实际型号和负载。`shared_buffers=512MB`、`work_mem=16MB`、`max_connections=80`；测试期间无其他压测任务。
- 初始产品验收配置：最多 100 个活动分支；每分支最多 250,000 个增量键、256 MiB 逻辑 delta；一次 apply 最多 10,000 行、32 MiB 逻辑写集。base/current/key/元数据计入逻辑字节，计算规则在 S05 固定；物理膨胀另行监控。
- 每次 overlay 执行的额外受控工作内存预算为 128 MiB；单 backend 总 context 峰值上限 256 MiB（本工作负载）。超过工作预算应溢出或明确拒绝，不能逐行无限追加。测试可降低配额来验证边界，但不能提高预算掩盖溢出。
- 默认 TTL/审计保留期在 S04 作为部署配置固定；验收使用 TTL=5 秒、GC 周期=1 秒、结果保留=60 秒的短配置。在 10 秒内进入禁止写入状态，20 秒内完成符合条件的回收；保留期内回执仍可查询。可控时钟测试需另有真实时钟边界测试。

### 12.2 内存与清理

固定 SQL/参数集合预热 50 次后记录 backend 全部 context 的 `used_bytes`，再执行 200 次，每 50 次取样。末次不得超过预热值加 `max(1 MiB, 5%)`；继续执行到 1,000 次后仍须满足同一预算，不能把增长解释为可接受的每次开销。500 行×256 字节的原复现必须包含其中。

再覆盖大扫描、密集 delta、rescan、RETURNING 和错误/取消路径。固定工作集经过清理后重复执行不应留下逐行对象；任何已定位泄漏都算 FAIL，即使尚未突破上述阈值。RSS 作为辅助指标，不能替代 context 所有权与 used_bytes。

按资源归属分别验收：语句结束或取消后，语句拥有的资源必须在 10 秒内回收，正常长连接可以继续存在；事务级锁在 COMMIT/ROLLBACK 后 10 秒内释放。显式事务中取消语句时，驱动先按 PostgreSQL 的错误恢复规则 ROLLBACK，再检查事务锁，不能要求取消本身释放所有事务锁。客户端断开后 10 秒内，对应测试 backend 和连接必须退出。临时文件按已声明的执行/事务生命周期回收；终态 delta 按 GC 保留策略单独判断。

### 12.3 性能场景与硬阈值

每组参考表与 overlay 结果必须相同；测试时间不包括 fixture 创建及建立对照副本。每场景预热后测量 5 轮，点查每轮至少 1,000 次，其余扫描/JOIN/写入/apply 场景每轮至少 30 个独立请求。apply 每个样本使用新草稿及对应的初始 MAIN，对照也重置，不能反复计时已成功请求的幂等空操作。每轮交替运行参考与候选，保存请求级原始样本；报告各轮中位值及同场景合并 p50/p95/p99、样本总数，分位数算法固定为 nearest-rank。p99 仅作诊断，硬阈值以表中的中位数和 p95 为准；不能用 5 个轮次总耗时代替请求延迟分布。

| 场景 | 输入 | 初始通过阈值 |
| --- | --- | --- |
| PERF-0：分支外开销 | 相同 PG 构建，扩展加载但不选分支，对照未加载扩展；点查、扫描、普通写 | 各场景中位时延比 ≤1.10；p95 比 ≤1.20 |
| PERF-1：空 delta | MAIN 200,000 行，普通列和 256 字节文本；点查、过滤、count、JOIN | 相对原生等价表，中位及 p95 比均 ≤2.0 |
| PERF-2：稀疏 delta | 同上，2,000 个变更键，含 I/U/D；点查、改后非 PK 过滤、扫描、JOIN | 中位及 p95 比均 ≤3.0，结果完全相等 |
| PERF-3：密集 delta | 20,000 与 200,000 个变更键，保持在分支配额内 | 中位及 p95 比均 ≤5.0；满足内存预算，无无限量物化 |
| PERF-4：规模增长 | N/M 为 20,000/2,000 与 40,000/4,000，同数据分布 | 比较/探测计数比和 5 轮中位时间比均 ≤3.0；不存在逐 MAIN 行遍历全部 delta 的路径 |
| PERF-5：分支规模 | 1/32/100 分支，每分支 100 个 delta 键 | 单分支点查/扫描的 100 分支对 1 分支 p95 比 ≤2.0；不扫描其他分支 payload |
| PERF-6：apply | 单表和两表；100/1,000/10,000 行，低于字节上限；同样 DML 的原生事务作对照 | 中位及 p95 比均 ≤5.0；超过行数/字节上限的负向测试在 MAIN 变动前拒绝 |

极短操作必须用固定大小批次计时，同时保存原始批次时延和客户端基线，不能比较计时分辨率以下的单次样本。此时每轮至少 30 个批次并满足上述请求数，按批次计算分位数，明确标注批次大小；参考与候选采用相同算法，不把批均值冒充单请求尾延迟。若同一场景五轮中位值的最大/最小比超过 1.25，标为测量无效，查明负载后重跑，不丢弃最慢样本挑最好一轮。

### 12.4 并发活性与压测核账

正常无争用 case 必须在 30 秒语句上限内结束。锁持有者释放后，等待者在 10 秒内前进或返回明确错误；超过期限即失败并输出锁图。重试最多 3 次，不能无限重试掩盖进展问题。

STRESS 的无冲突子阶段连续运行至少 5 分钟，每种声明参与的操作至少 100 次成功完成；冲突子阶段按精确错误类型计数，仍须有成功业务进展。除明确被取消/拒绝的请求，所有收到提交成功回执的操作都进入核账；显式 discard 是可解释终结，无法找到增量去向不是可接受结果。

旧 `test/bench/apply_contention.sql` 的角色控制、分支选择、错误处理及最终断言必须先审查修订。存在合法 apply 的负载中，MAIN 新行可能是正确结果；单独要求 MAIN 行数不增长不能证明没有写穿。新的验收以请求账本和具体数据变化为准。

### 12.5 需求覆盖与真实工作流预算

- S04 冻结至少一个真实目标工作流及样本周期，记录表定义、SQL 形态与调用次数。支持写入覆盖率为“已支持形态的调用次数 / 样本内全部业务写请求次数”，目标 ≥80%；另报按不同 SQL 形态计算的覆盖率。所有关键业务链路必须可完成，不因总频率低而略去其 FK、upsert 或事务需求。
- S04 只评估计划范围；S11 以实际重放和独立结果对照报告当前已实现覆盖率，S15 在 M2 必需能力齐备后验证最终覆盖率与关键链路。每个未支持请求保留在分母并说明影响。新增样本或改变产品范围应更新版本并重算，不能事后挑选通过样本。
- S09 在隔离副本中完成 5 个来自目标工作流的不同任务。S21 在至少 5 个工作日内，由真实 Agent/内部业务使用者按公开接口完成至少 20 个独立任务，完成率 ≥90%；其中至少 10 个经过审阅并成功 apply。重复请求同一回执只计一次，自动回归循环不计用户采用。
- 试用不要求接入生产数据，可用获授权的脱敏副本；记录全部尝试、耗时、最终状态、人工介入和失败原因。完成表示结果经业务期望核对、无需维护者操作内部表；未完成任务不能从完成率分母删除。任何隔离、越权或静默丢数据问题仍按正确性门禁失败，不能由 90% 完成率豁免。
- 这些采用数值同样是初始目标，S04 冻结；S21 的一份真实试用账本不必在两个环境中重复计为两次采用。技术 E2E 仍须在两个新集群重放；最终候选必须兼容经试用的流程，改变流程/支持范围时重新试用受影响任务。

### 12.6 同实例 MAIN 影响预算（G05）

原计划尚未给出这部分具体数值，保持 OPEN。S04 选择部署与目标前台 workload，最迟 S24 开始前冻结：Agent 角色连接数、活动查询并发、statement/lock timeout、可实施的 CPU/IO 控制方式，以及固定 MAIN 负载的 p95/吞吐退化上限和测量时长。没有实际限流手段时不得把观测指标写成已保证的硬隔离。
